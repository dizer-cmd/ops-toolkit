# Evaluation — first live run, 16 September 2026

Tools at v1.0.0, `claude-opus-5`, 20 synthetic records, 24 API calls,
50,658 input / 10,029 output tokens, **$0.50**. Median latency 6.2s, max 16.7s —
inside the `sla_seconds` declared in both tool specs.

The run is recorded in `runs/audit.jsonl`. This document is the part that
matters: what disagreed, who was right, and what changed as a result.

---

## Headline

| | case-intake | complaint-triage |
|---|---|---|
| **review recall** | **100%** | **100%** |
| review precision | 90% | 87.5% |
| missed (should have reached a human, did not) | **0** | **0** |
| field accuracy | 83–100% | 62–75% |

Recall is the number the library is built around, and it held. Nothing that
should have reached a person was cleared automatically.

Field accuracy looks weak, particularly on complaints. The rest of this document
is why that number is not what it appears to be.

---

## The finding

Nine field mismatches. On investigation, **six were defects in the specification,
not errors by the model** — either the answer key asserted something the source
text did not support, or it contradicted the prompt it was graded against.

This is what an evaluation is for, and it is the reason the answer key is written
before the first run rather than after it. Writing the key afterwards would have
produced a high score and found nothing.

**The temptation to resist is adjusting the key until the score improves.** Each
disagreement below is adjudicated on its merits, with the decision recorded. In
one case the key stands and the model is overruled; in two, the model's reading
was reasonable but the prompt was silent, so the prompt changed rather than the
key.

---

## Adjudications

### 1. `CASE-0003` priority — key said P2, model said P3 → **model right, key corrected**

A first contact with no client reference. Nothing in the P1–P4 ladder makes a
missing reference urgent: it blocks the work rather than making it time-critical,
and it already forces human review.

The key had conflated two different axes. Priority is time pressure; review is
consequence. Both prompts now say so explicitly.

### 2. `CASE-0004` priority — key said P1, model said P2 → **model right, key corrected**

A complaint written as a chase. The key rated every complaint P1; the prompt's
own definition of P1 is "vulnerability, distress, a deadline at risk, or an
irreversible request" — none of which describes a complaint on the day it
arrives.

A new complaint starts an eight-week clock. On day one nothing is at risk. It
reaches a human regardless, which is the control that matters.

*Decision recorded:* **a complaint is not automatically P1.** If everything
serious is P1, P1 stops distinguishing the cases that genuinely cannot wait —
the bereavement, the withdrawal, the deadline already blown. Rationing the top
priority is what makes it useful.

### 3. `CASE-0011` — cleared by the key, flagged by the model → **model right, key corrected**

Flagged for `no_claimant_contact_details`: unlike `CASE-0001`, of which this is a
resubmission, it carries no contact details at all. That is a genuine gap in the
row and the key had missed it.

Worth being precise: **the duplicate is still undetected.** The model flagged a
different fact for a different reason. Cross-row duplicate detection remains
roadmap item 1 and this run is not evidence against that.

The model's second reason — `possible_ill_health_indicator_signed_off_nine_days`
— was over-reach, and is dealt with in adjudication 8.

### 4. `CMP-0103` category — key said `service_quality`, model said `unclear` → **model right, key corrected**

A carer writing for a brother with a learning disability, asking that
correspondence be redirected. Re-reading it: **no service failure is alleged
anywhere.** It is an access request made on someone's behalf. The key had
asserted a category the document does not support.

This also exposed a real gap: the category vocabulary has no slot for a
reasonable-adjustment or access request. Logged to `ROADMAP.md` rather than
invented in the middle of an evaluation — one observation is not enough to design
a vocabulary change, and `unclear` plus a safeguarding referral already routes it
to the right person.

### 5. `CMP-0104` category — key said `outcome_dispute`, model said `unclear` → **model right, key corrected**

The letter threatens the ombudsman, names a solicitor, and **never states what
the complaint is about.** The key had inferred a category from the file
reference. The model's output said so directly:
`substance_of_complaint_unclear`.

`unclear` plus `escalate_legal` is the honest answer.

### 6. `CMP-0107` category and next_action — key said `service_delay` / `acknowledge_and_investigate`, model said `process_complaint` / `escalate_senior` → **model right, key corrected**

What is overdue is the **final response to a complaint**. That is the complaints
process, by the prompt's own definition, and the prompt's own `next_action`
vocabulary routes process complaints to a senior owner.

The key had read the surface topic and was internally inconsistent with the
vocabulary it shipped with. The model was more faithful to the specification than
its author was.

### 7. `CMP-0102` and `CMP-0106` severity — key said `high`, model said `medium` → **key stands, prompt corrected**

`CMP-0102` is a conduct allegation against a named handler. `CMP-0106` is a
complaint that was never acknowledged in three weeks.

The severity ladder mentioned neither, so `medium` was a reasonable reading of
what was written. But both belong at `high`, for reasons that needed stating
rather than inferring:

*Decision recorded:* **a conduct allegation is `high` as a floor**, however
calmly written. A complaint about a person cannot sit in the ordinary queue,
because the ordinary queue may be worked by the team it concerns. The cost of
under-rating is that the person complained about reads the complaint about
themselves — an asymmetry that makes the floor worth paying for in false
positives.

*And:* **an unacknowledged complaint is a clock at risk.** If someone wrote weeks
ago and heard nothing, an acknowledgement deadline has already been missed and
the response clock has been running with nobody counting it.

Both are now written into the prompt.

### 8. `CMP-0108` vulnerability and next_action — model said `safeguarding_referral`, key said `acknowledge_and_investigate` → **model overruled, key stands, prompt corrected**

The complainant asks to be reimbursed for two unpaid days off work. The model
read that as financial hardship and made a safeguarding referral.

**That is financial loss being claimed, not financial hardship being disclosed.**
The prompt listed "financial hardship" without defining it and the model
reasonably reached for it. Treating every lost-earnings claim as a safeguarding
matter would flood safeguarding and devalue the referral for the people who need
it.

The prompt now draws the line: hardship means the complainant indicates they are
struggling — cannot afford essentials, in debt, reliant on benefits. The same
distinction now applies to health in `case-intake`: the injury a claim is *about*
is subject matter, not a disclosure. That also resolves adjudication 3's second
reason.

This is the one where the model was wrong and the key held.

### 9. `CMP-0101` — cleared by the key, flagged by the model → **model right, key corrected**

Flagged for `clock_start_date_ambiguous`: "I first wrote to you on 20 August"
does not establish whether that letter was a formal complaint — and the answer
decides when the regulated clock started.

That is a real operational question and it belongs to a person.

## A limitation this run exposed in the evaluation itself

With `CMP-0101` correctly flagged, **all eight synthetic complaints now reach a
human.** A tool that flags everything has no automation value, and a precision
figure computed against a set where every item should be flagged measures
nothing.

That is an artefact of the dataset, not a property of the tool. The complaint set
was built entirely from awkward cases — that is what made it useful for recall —
and it therefore cannot measure precision at all. Before the next evaluation it
needs ordinary complaints added: routine, well-evidenced, unambiguous ones that
*should* clear automatically. Logged to `ROADMAP.md`.

Stating this is more useful than reporting 87.5% precision as though it meant
something.

## Changes made

**`case-intake` 1.0.0 → 1.0.1**
- priority defined as time pressure only, explicitly separate from review
- a new complaint is not automatically P1
- a missing reference is a review matter, not a priority matter
- the injury being claimed is not a vulnerability disclosure
- answer key corrected: `CASE-0003`, `CASE-0004`, `CASE-0011`

**`complaint-triage` 1.0.0 → 1.0.1**
- severity floors added for conduct allegations and unsent acknowledgements
- financial loss claimed distinguished from financial hardship disclosed
- answer key corrected: `CMP-0101`, `CMP-0103`, `CMP-0104`, `CMP-0107`

**Harness**
- unsupported JSON Schema keywords stripped on the wire, enforced locally
  instead, with a test (this run's first attempt failed 400 on every case for
  `maxItems`)

**Roadmap additions**
- a category for reasonable-adjustment and access requests
- ordinary complaints added to the evaluation set so precision can be measured

Nothing was changed to improve a score. Each change above is a decision about
what the tool should do, recorded so it can be argued with.

## The regression was mine

`CASE-0011` was cleared automatically when the v1.0.1 key said it must reach a
person.

The model was not careless. It recorded `missing_information:
["claimant_contact_details"]` — it saw the gap and put it exactly where that
field exists to put it. It then did not escalate, because **the prompt never says
that missing information requires escalation.** The escalation policy lists
vulnerability, withdrawal, complaints, a missing client reference, contradictory
dates and non-English content. Missing contact details is not among them.

At v1.0.1 the key was changed to require review on the strength of the model
having flagged it once, without adding the rule that would make it required. The
key asserted behaviour the specification did not ask for, and the next run found
the gap.

This is the failure this document warns about in its own opening section, made by
its own author one section later. It is left in rather than edited out: the
discipline of not tuning the key to the model is easy to state and evidently easy
to breach.

**On the merits the revert is also correct.** `CASE-0011` carries a present,
well-formed client reference, so the contact details are on the file. The gap is
worth recording; it is not worth a person's time. The prompt now states that a
populated `missing_information` is a record, not a trigger.

## Where the key had not caught up with its own prompt

Three more mismatches were the same shape: v1.0.1 established a principle, the
model applied it consistently, and the key did not.

- `CASE-0009`, `CASE-0012` priority — v1.0.1 ruled that blocking is not urgency,
  and applied it to `CASE-0003` only. A missing attachment and a translation
  requirement block the reply without putting anything at risk. **Key corrected
  to P3.**
- `CMP-0101` severity — v1.0.1 added "an unacknowledged complaint is a clock at
  risk, therefore `high`", then left the key at `medium`. **Key corrected.**

Three went the other way, and the prompt was sharpened instead:

- `CASE-0007` priority — a stated deadline of 05/03/2026 on a letter dated
  September may already have passed. That is a deadline at risk. The model rated
  it P2; the prompt had not said a possibly-elapsed deadline counts. **Rule
  added.**
- `CMP-0104` severity — the model escalated 62 days with no stated commitment to
  `critical`. That is now reserved for a deadline that has demonstrably gone: a
  stated commitment, and elapsed time exceeding it. Time merely passing is
  `high`. **Rule added.**
- `CMP-0108` category — genuinely mixed: a disputed decision *and* cancelled
  appointments. **Tie-break added:** classify by what the complainant asks to
  have changed, not by how much of the letter each grievance occupies.

## Two things run 2 proved

**The prediction held.** Run 1 closed by predicting that `CMP-0108` would return
`acknowledge_and_investigate` rather than a safeguarding referral if the
loss-versus-hardship wording landed. It did — `vulnerability_indicated` false,
`redress_sought` true, `next_action` as predicted. The one place the model was
overruled is the one place the fix was verified in advance.

**Validating twice earned its keep, unplanned.** `CMP-0103` came back with a
288-character summary against a 280 limit. `maxLength` is one of the keywords
stripped on the way to the API, because structured outputs reject it — so the
platform could not have caught this. The local contract check did, raised
`schema_violation`, and sent the case to a human instead of passing a malformed
row downstream.

That is the argument in `GOVERNANCE.md` § 2 happening for real rather than being
asserted.

## The stopping rule

Two runs in, the risk stops being a bad prompt and starts being endless tuning.
So the condition for stopping is set here, before the next run, rather than after
seeing it:

1. **Review recall at 100% on both tools.** Nothing else compensates for this.
2. **No known contradiction between a prompt and the key it is graded against.**
   Every disagreement must be resolvable as a genuine judgement call, not as one
   of the two documents being out of date.
3. **No schema violations** beyond the one already understood.

Field accuracy is deliberately **not** on the list. What remains is where the
boundary between `high` and `critical` sits, and which of two true categories
leads — questions two experienced handlers would answer differently. Driving
those to 100% would mean tuning the key until it agrees with the model, which
measures nothing.

If run 3 meets the three conditions, the tools ship at 1.0.2 and everything
further goes to the roadmap — starting with adding ordinary complaints, so that
precision becomes measurable at all.

## The finding: a rule that lives only in the documentation is not a rule

`CASE-0003`, `CASE-0006` and `CASE-0009` were all cleared automatically. In all
three the model saw everything — it populated `missing_information` correctly in
each case — and escalated none of them.

The cause is not wording. **`case-intake`'s escalation policy lives in
`TOOL.md`, which the model never sees.** The prompt's numbered rules encoded some
of the published triggers and not others; `out_of_scope` and
`referenced_attachment_absent` were in neither.

Runs 1 and 2 passed because the prompt invited the model to escalate whenever it
was unsure, and it inferred the missing rules from general caution. v1.0.2 added
one sentence — *"escalate only where one of these rules says to"* — which removed
the inference. The policy gap had been there since v1.0.0; that sentence only
made it visible.

Three evaluation runs of a governed tool were carried by a policy nobody had
given the model.

## The fix is structural, not another prompt edit

The published policy is now **injected into the system prompt verbatim** at
`{{escalation_policy}}`, read straight from the `## Escalation policy` section of
`TOOL.md`. One text, read by the governance reviewer and by the model. They
cannot drift, because they are the same characters.

Consequences, all deliberate:

- `prompt_sha` now covers the policy. Editing the table in `TOOL.md` produces a
  new prompt version, so the audit trail cannot attribute decisions made under a
  new policy to the hash of the old one.
- `verify` fails any tool that publishes a policy the prompt does not include.
  This is now a build gate, not a convention.
- Two triggers that were never written down anywhere have been added to the
  published policy: out-of-scope correspondence before it is returned to sender,
  and a referenced attachment that is not present.
- Three tests cover it: every tool publishes a policy, the published text is what
  the model receives, and editing it changes the version.

## The recurring contract breach

`CMP-0108` failed its contract for the second run running:
`review_reasons[1]: 68 chars, max 64`.

The limit was wrong, not the output. The model's reasons are genuinely
informative — `secondary_grievance_service_quality_consultant_report_not_considered`
says more than a truncated version would. **Raised to 100 characters** in both
schemas, and the prompt now states the limit in words as well, since the API
cannot enforce it.

Twice is a defect. Once is an incident.

## Left alone

`CASE-0008` priority: key says P2, model says P3. Under the stopping rule this is
a judgement call rather than a defect, and it stays. Two handlers would disagree
about whether an ambiguous person reference and conflicting file information make
a case a this-week job or a normal-queue one.

Escalation policy injected from `TOOL.md` into both prompts; `out_of_scope` and
`referenced_attachment_absent` published as triggers; `review_reasons` limit
raised to 100; `verify` gate and three tests added.

### The two remaining disagreements are left standing

- `CASE-0006` priority — key `P4`, model `P3`. An out-of-scope boiler enquiry.
  `P4` means "no action needed beyond filing", but returning correspondence to
  sender *is* an action, so the model has a point and the key may be the sloppier
  of the two readings.
- `CASE-0010` routing — key `intake_team`, model `legal`. A withdrawal request.
  Whether closing a claim is an intake task or a legal one is a question about
  how the business is organised, not about the text.

Neither is a contradiction between the prompt and the key; both are places the
prompt is **silent** and two reasonable readings exist. Under the stopping rule
they stay. Picking one in order to reach 100% would be tuning the specification
until it agreed with the model, and the resulting number would mean nothing.

Both are recorded in `case-intake`'s `Known limits` as open questions for the
tool's owner — which is what an unresolved business rule should look like, rather
than a silently chosen default.

## What the whole evaluation cost

84 live calls across four runs. 216,140 input and 35,069 output tokens — **$1.96
in total**. Run 4 latency: median 5.7s, max 14.0s, inside both declared SLAs.

Eight distinct prompt versions appear in `runs/audit.jsonl`. Every decision in

## What four runs actually taught

Three of the four runs found a defect in the **specification**, not in the model.
The model was wrong once — `CMP-0108`, where it read a reimbursement claim as
financial hardship — and that was traced to a word the prompt had left undefined.

The two most useful findings were not about prompting at all:

1. **A rule that lives only in the documentation is not a rule.** Three runs of a
   "governed" tool were carried by an escalation policy the model had never been
   shown. It now cannot happen quietly: the published policy *is* the prompt
   text, `verify` fails a tool where it is not, and three tests cover it.
2. **Changing the answer key to match one run is how an evaluation stops
   measuring anything.** Recorded in run 2, where doing exactly that cost a point
   of recall on the following run — left in the document rather than tidied away.

Both are recorded because they generalise past these two tools. Neither would
have appeared without running the thing for real against a key written in
advance.
